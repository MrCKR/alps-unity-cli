# 运行时调试闭环

只在任务要求在已打开的 Editor 中定位、证明、验收或复测运行时行为时读取本文件：行为与预期不符、需要验收或验证一次运行时行为、需要证明某个业务输入确实被业务接收、需要某个方法在调用边界的参数或结果、需要暂停现场查看栈与对象，或需要按同一输入复测并比较证据。日常的实例、descriptor、envelope 与超时规则见 [操作协议](operation-protocol.md)。

本文件只讲闭环步骤与证据判断，不列 Tool 与参数。能力仍从当前实例的统一 catalog 发现：先读取分组概览，再按关键词搜索并用 `tools describe` 学习所选能力，然后提交调用。

## 九步闭环

1. **定义预期与反例。** 先写下可证伪的预期：哪个对象、哪个字段、哪个线程、哪个时钟窗口应该出现什么。同时写下至少一个反例——出现什么就说明预期错误。还要声明本次需要的来源覆盖与证据量；没有覆盖声明时，否定结论和整窗结论都不能成立。
2. **读取源码与 catalog。** 读业务源码确定执行域、逻辑权威（谁拥有该状态的真值）、线程模型、输入入口与时钟；读当前 catalog 确认可用能力、状态约束和副作用。源码只用于形成假设，它本身不是运行时证据。
3. **建立 owner 与 readback。** 为本次调查建立一个 session，用只读观察回报当前状态，并把准备动作与观察分开记录。需要跨越 Play 边界时先登记观察再进入 Play。没有 readback 的准备不算已准备。
4. **选择证据与快照或暂停。** 按假设选择证据来源：命中捕获的字段、参数或返回值，字段读取，事件流，日志或调用栈。需要一次静态现场时使用快照式捕获；只有在确实要继续读取现场、评估或改写时，才显式选择有界或无界的暂停。只有在必须有代码逻辑时才执行临时程序，并把它当作本次调查的输入，而不是产品的正式实现。
5. **设置检查与监听式注入。** 用命名 check 或监听式注入声明要看什么、从哪个来源与位置看、命中次数或触发条件是什么，然后执行业务操作。业务操作成功返回不等于业务接收了输入，必须用第 4 步选定的证据证明「确实接受」。
6. **定位首个可证明偏离。** 按时间顺序找出第一个有证据支持的偏离，并把它表达成可证伪假设。需要时改参数、跳过原方法、写结果或热替换，但干预要最小化并保留旧结果、旧配置与边界，不得用干预掩盖原始证据。
7. **恢复与同输入复测。** 先恢复必要条件（解除暂停、释放设备、还原被改的值），再用相同业务输入复测，并按预先声明的对齐键比较两次 trace：来源、位置、对齐键、值路径与时钟都必须一致，不能用全局序号、对象地址或墙上时间代替。
8. **区分结论与观察扰动。** 结论只有 `passed`、`failed`、`indeterminate` 三种；证据缺口、采样、截断、未排空的边界或相关配置变化都会得到 `indeterminate`。还要区分「条件本身不同」与「观察改变了时序」：暂停、监听与高频捕获都会扰动执行，必须说明扰动是否足以解释差异。
9. **stop 并核对清理与保存 recipe。** 结束调查时停止会话并读取清理报告，核对仍未回收的定义、监听、暂停、输入设备与编译产物。recipe 与源码作为可重新加载的配置保存，不能把它当成游戏状态快照。定义在 Domain Reload 后恢复但不带任何运行中的资源，Play exit 与 Editor 重启会使其失效。

## 各类证据能证明什么

- **Console。** Unity 自身记录的编译与运行期日志快照。它证明 Unity 报告过这条信息，不证明业务语义、调用顺序或输入是否被接受。快照读取不改状态也不清空；清空是独立的状态修改。
- **Hook。** 在 exact target 与固定 revision 上证明目标方法确实被调用、调用发生在哪个线程，以及调用边界处的参数、字段与返回值。它不证明调用之后的业务后果；采样、预算与覆盖缺口意味着「没有命中」不等于「没有调用」。
- **字段读取与写入。** 有界字段路径证明读取时刻该字段的值；读取不执行 getter、不运行序列化，因此只证明值本身。写入是结构化干预，会改变对象或调用现场状态，必须按干预记录并在复测前还原。
- **暂停。** 证明命中的线程停在调用边界，可以读取现场栈、评估表达式、改参数或写结果。暂停是有界或无界的显式选择。解除暂停是解除等待而不是抢占：同步代码仍会运行完，无法证明已解除时必须报告 pending 或 unknown。
- **日志与事件流。** 统一事件真值是跨定义共享的有界环形缓冲，给出顺序、来源、线程与时钟，并在溢出时如实报告缺口。日志订阅记录真实回调线程，不能假设回调线程就是业务边界，也不能假设所有业务调用都被保留。
- **外部 Profiler。** CLI 之外的时间、分配与帧成本证据。它能证明开销与热点，不能给出某个业务调用边界的确切参数、顺序或因果，也不能替代事件真值。本文件的证据判断只针对本 CLI 自己的证据来源。

## 调试能力族与选择

能力按族发现。下表只给族、证据范围与选择依据；每族的准确输入、约束、可用状态与错误码由当前 catalog 的 `tools describe` 给出。

| 族 | 提供的证据 | 什么时候选它 | 不能证明 |
| --- | --- | --- | --- |
| `debug.session.*` | 谁是本次调查的资源 owner，以及停止后的清理报告 | 调查开始与结束 | 业务状态本身 |
| `debug.hook.*` | 目标方法确实被调用、发生在哪个线程、调用边界的参数、字段与返回值 | 需要调用边界事实 | 调用之后的业务后果 |
| `debug.program.*` | 在声明执行点做一件小事，可跨帧、可按步推进 | 必须在指定相位或帧动作 | 抢占已经在运行的同步代码 |
| `debug.code.flow.*` | 一次调用内跨帧执行，每次等待带独立的满足/超时事实 | 要“做 A、等 X、做 B”而不想管定义 | 业务结论；它不替你做判定 |
| `debug.events.read` | 顺序、来源、线程、时钟与缺口 | 需要时序与覆盖缺口 | 业务语义 |
| `debug.thread.list` | 实际观察到的线程与观察范围 | 判断线程归属 | 全部 managed 线程 |
| `debug.pause.*` | 命中的线程停在调用边界，可读现场栈、评估表达式、改写值 | 需要静态现场 | 线程已被强制停止 |
| `debug.value.read/write` | 读取时刻某字段的值 | 需要 readback 与基线 | getter、序列化与业务含义 |
| `debug.run.*` | 命名检查、三态结论与同输入比较 | 需要可证伪结论 | 没有覆盖的否定结论 |
| `debug.input.*` | 输入是否被业务接收 | 需要驱动输入 | 业务是否产生预期效果 |
| `debug.console.read/clear` | Unity 自身记录的日志快照 | 需要 Unity 已报告的事实 | 调用顺序与输入是否被接受 |

证据不足时不要换族猜结论：先补覆盖，或改选能覆盖的族。

执行域：调试族全部声明 Editor 目标，只在 Editor 与其 Play 模式中可用。Player 构建提供的是另一组运行期能力，不含监听、程序、暂停、字段与输入注入。

## 跨帧流（`debug.code.flow.*`）

`debug.code.execute` 是同步到底：代码在主线程跑完才返回，运行期间帧不推进，所以里面无法等帧。需要“做 A、等 X、做 B”时用 `debug.code.flow.execute`：它编译一次，然后在中央 editor tick 上逐帧推进，Edit 与 Play 都可用，不靠 `StartCoroutine`。

代码体是 `public static IEnumerator Run(string argsJson)`，可用的 using 已包含 `UnityCli`。跨帧只能通过 `DebugFlow` 表达：

```csharp
yield return DebugFlow.NextFrame(3);                     // Play 模式等 3 次 Time.frameCount 增长；Edit 模式退化为 3 个 editor tick
yield return DebugFlow.After(250, 2000);                // 单调时钟，超时必填
yield return DebugFlow.Until(() => actor.Hp <= 0, 5000); // 条件，C# 委托
yield return DebugFlow.UntilSignal("hit-confirmed", 3000);
yield return DebugFlow.UntilLog("BattleStart", 5000);       // 日志子串命中（可选等级 log/warning/error）
yield return DebugFlow.All(waitA, waitB);                // 全部满足
yield return DebugFlow.Any(waitA, waitB);                // 任一满足
yield return DebugFlow.Return(value);                    // 结束并返回值
```

每个等待都必填超时，没有默认值；条件写 C# 委托，不提供字符串表达式。等待结束后 `DebugFlow.Last` 是可读的 `DebugFlowWaitResult`：C# 属性 `Satisfied`、`TimedOut`、`ElapsedMs`、`Samples`、`LastObserved`。超时**不抛异常**，它是一次可分支的结果；条件本身抛异常才让流失败，`failureTag` 为 `predicate-exception`。

结果规则：

- 只有 `completed` 返回 `ok:true`，带 `result`、`steps`、`samples`。
- `running` 返回 `E_DEBUG_FLOW_PENDING`：用**同一个** flowId 调 `debug.code.flow.wait` 续等；重新提交会产生第二条流，不是恢复路径。
- `failed`、`timed-out`、`cancelled`、`aborted` 分别返回 `E_DEBUG_FLOW_FAILED`、`E_DEBUG_FLOW_TIMED_OUT`、`E_DEBUG_FLOW_CANCELLED`、`E_DEBUG_FLOW_ABORTED`，`details` 带 `flowId`、`status` 与终态事实。
- `debug.code.flow.cancel` 可重复调用；已终态时返回同一终态，不重写历史。

预算与存活：

- `waitMs` 只约束本次调用等多久；到期不取消流。
- `flowBudgetMs` 是流自己的生命周期预算，从首次 tick 起算，**不含编译**，也不计主线程被暂停占用的时间。
- 同时最多 2 条流每 session、4 条每 Unity 实例；超限立即拒绝而不排队。
- 流不跨 Domain Reload、Editor 重启或 Play 段结束存活；只能重新提交。

并发与可信度：每条流都在主线程上采样，多开只会互相挤占帧时间。要精确测量“第几帧命中”，并发越低越准；多开适合互不干扰的独立场景。返回值有字节上限，超出时报告 `resultTruncated`。

## 边界与遗留

- 运行时调试不修改业务源码、不创建业务程序集、不改业务资源。要让实验中的替代结果成为正式修复，必须作为新的明确业务工作重新实现与验收。
- 只读观察同样占用 session 资源；监听、暂停与设备都属于资源 owner。每次调查结束都必须 stop 并核对残留，并记录本次已加载且不可回收的编译产物。
